# Tool 1 — Multilingual Planning & Pre-Generation System
## PRD + README + Technical Implementation Context

## 1. Overall Project Goal

We are building a software / automation system that starts from a script and ends as published YouTube videos.

This is not only a single-channel workflow.

The real goal is:

- create one master video concept
- reuse the same visual assets across many language channels
- generate one localized final video per language
- keep narration, timing, and final assembly correct for each language

The same content will be published across multiple channels in different languages, using:

- different translated scripts
- different generated narrations
- different subtitle timing
- different final localized videos

The key challenge is that each language takes a different amount of time to say the same semantic content. Because of that, the same final timeline cannot be reused directly for all narrations.

Tool 1 exists to solve the planning side of that multilingual challenge.

## 2. The Two-Tool Architecture

The whole project is now organized around two major tools.

### Tool 1 — Multilingual Planning & Pre-Generation System
Tool 1 is responsible for all work that happens before final asset assembly.

It handles:
- translation workflow
- voice generation workflow
- subtitle timing
- master scene planning
- localized timeline generation
- prompt list generation
- artifact export for downstream assembly

### Tool 2 — Multilingual Final Video Assembly System
Tool 2 is responsible for taking:
- shared image/video assets
- one localized narration
- one localized timeline

and producing the final video for that language/channel.

Tool 2 does not decide scenes.
Tool 2 executes the plan created by Tool 1.

This document focuses on Tool 1, but briefly explains Tool 2 where needed so the relationship stays clear.

## 3. What Tool 1 Is

Tool 1 is a hybrid planning system.

It combines:
- local software / automation
- AI-agent reasoning
- a human asset-generation step later in the workflow

Tool 1 starts from:
- source script
- translation configuration or translated scripts
- voice generation configuration or generated narrations

And it produces:
- shared semantic scene structure
- localized subtitle timing
- localized timeline files
- shared prompt list for asset generation

Tool 1 does not produce the final video.
Tool 1 does not directly produce the final image/video assets.
Those assets are still assumed to be generated by a human after the prompt list is ready.

## 4. Why Tool 1 Needed to Change

In the single-language version, Tool 1 could output:
- one SRT
- one `timeline.json`
- one prompt list

That is not enough anymore.

Now the project must support:
- many channels
- many languages
- one shared visual identity
- one shared asset pool
- many narrations with different durations

So Tool 1 must now separate:

- the semantic scene structure, which should be shared
from
- the timing layer, which must be language-specific

That is the core architectural change.

## 5. New Core Multilingual Model

Tool 1 must now think in two layers.

### Layer A — Global / shared scene structure
This is created once.

It defines:
- scene ids
- scene order
- semantic meaning
- asset type
- visual intent
- prompt generation basis

This layer should be language-independent.

### Layer B — Language-specific timing layer
This is created once per language.

It defines:
- localized narration timing
- localized subtitle timing
- localized scene start/end/duration
- the same scene ids, but with new durations

This means the core rule becomes:

- **scene identity is shared**
- **scene timing is localized**

That is how the same assets can be reused across many channels.

## 6. Clarifying Option A

The preferred solution is Option A.

Option A means:

- one language defines the master scenes
- those scene ids become global
- prompts are generated once from the master scenes
- assets are generated once from those prompts
- every other language reuses the same scene ids and shared assets
- each language gets its own localized timing file
- Tool 2 later retimes the shared assets to match the localized narration

So what stays fixed:
- scene ids
- scene order
- prompt list
- generated assets

What changes per language:
- translated script
- narration
- subtitle timing
- scene durations

That is the correct multilingual architecture.

## 7. Merge of Translation and Voice Generation Into Tool 1

A major new decision is that translation and voice generation should now be considered part of Tool 1.

Previously, they were done outside the workflow.
Now they should be merged into the Tool 1 system boundary.

This does not necessarily mean Tool 1 must internally invent those models.
It means Tool 1 must orchestrate those processes as part of the overall workflow.

So Tool 1 should now support:

### 7.1 Translation stage
For each target language, Tool 1 should be able to:
- translate the script
- preferably preserve scene correspondence or support scene-locked translation after master scenes exist

### 7.2 Voice generation stage
For each target language, Tool 1 should be able to:
- generate the localized narration
- store it in the project structure
- pass it forward to subtitle alignment and localized timeline generation

### 7.3 Why merging these stages matters
If translation and voice generation remain external and informal, the system becomes harder to automate and harder to track.
By integrating them into Tool 1, the workflow becomes:
- more trackable
- more reproducible
- easier to visualize in the UI
- easier to automate later

So Tool 1 is now not just:
- subtitle timing + scene planning

It is:
- translation + voice generation + timing + scene planning + prompt planning

The interface is similar in spirit to a Trello board or column-based production dashboard:
- each step of the workflow is represented as a column or stage
- the operator can clearly see what stage comes next
- the operator can see progress happening through the pipeline
- the system can make each artifact visible at the correct stage

This UI concept matters because Tool 1 is not just code running invisibly.
It is also a guided workflow system.

### The purpose of the pipeline interface
The pipeline interface should make it easy to understand:
- what has already happened
- what is currently running
- what artifacts were produced

- what stages are fully automated vs partially automated

## 9. What Parts of Tool 1 Are Software, AI, and Human

This distinction must be explicit.

### 9.1 Application / automation work
These are handled by actual software:

- project creation
- file management
- translation orchestration
- TTS orchestration
- subtitle alignment
- SRT generation
- chunking if needed
- AI CLI / agent orchestration
- merge and validation logic
- localized timeline generation
- artifact export
- workflow UI state updates

### 9.2 AI-agent reasoning work
These are the reasoning-heavy steps:

- master scene planning
- master scene JSON creation
- prompt generation
- optional language-structure assistance in special cases

### 9.3 Human work
This remains explicitly human:

- reviewing outputs when desired
- generating the actual images/videos from the final prompt list

That means Tool 1 should automate planning up to the handoff for visual asset generation.

## 10. High-Level Workflow of Tool 1

The new Tool 1 workflow should be understood like this:

**source script > master scene planning flow > prompt list creation > human generates shared assets once > for each target language: translation > voice generation > subtitle alignment > localized timeline generation**

This means Tool 1 has both:
- a master/shared flow
- a per-language localization flow

## 11. Tool 1 Operating Modes

Tool 1 should have at least two main modes.

### 11.1 Master Build Mode
Used once for the source/master language.

Purpose:
- define the global scenes
- define the prompt list
- define the shared asset plan

Outputs:
- `master_scenes.json`
- `prompt_list.txt`
- optional source SRT
- optional source timeline
- `asset_manifest.json` recommended

### 11.2 Localization Build Mode
Used once per target language.

Purpose:
- translate the script
- generate localized narration
- align localized narration
- compute localized scene timing against the existing master scenes

Outputs:
- localized script
- localized narration
- `srt_LANG.srt`
- `timeline_LANG.json`

## 12. Core Output Artifacts of Tool 1

### 12.1 Shared artifacts
Created once.

#### `master_scenes.json`
The global semantic scene structure.

Should contain:
- `scene_id`
- scene order
- source text reference
- asset type
- visual intent
- notes

#### `prompt_list.txt`
The shared prompt list used to generate the visual assets.

Rules:
- 1 prompt per line
- scene order preserved
- created once from master scenes

#### `asset_manifest.json` (recommended)
Maps:
- scene ids
- asset ids
- asset file names / expected files

This will help Tool 2 map shared assets to localized timelines.

### 12.2 Per-language artifacts
Created once per language.

#### `script_LANG.*`
Localized script, ideally scene-aware.

#### `narration_LANG.*`
Localized narration generated by Tool 1’s voice stage.

#### `srt_LANG.srt`
Localized aligned subtitle file.

#### `timeline_LANG.json`
Localized timing file for the existing scene ids.

This file must keep:
- the same scene ids
- the same scene order
- new language-specific timing

## 13. Why `master_scenes.json` Matters

This file is what makes multilingual reuse possible.

Without it:
- each language could create different scenes
- prompt reuse would be unstable
- asset reuse would be unreliable

With it:
- scenes are fixed globally
- visual identity is stable
- prompts are generated once
- assets are generated once
- only timing changes per language

This is one of the most important architectural artifacts in the whole project.

## 14. Why `timeline_LANG.json` Matters

This file exists because different narrations take different amounts of time.

The assets stay the same.
The scene identities stay the same.
But the durations change.

So each language needs its own:
- scene start
- scene end
- scene duration

That is exactly what `timeline_LANG.json` provides.

This is the file Tool 2 will later use to retime the shared visuals for a specific language.

## 15. Preferred Translation Model

For the multilingual workflow to stay strong, translation should ideally preserve scene correspondence.

The best model is:

- define master scenes first
- then translate scene-by-scene
- then generate narration per localized scene set
- then align localized narration back to those same scene ids

This gives Tool 1 much stronger multilingual stability.

## 16. Role of AI CLI / Agent Tools Inside Tool 1

Tool 1 should be designed to orchestrate AI CLI / agent tools instead of relying on browser chat.

This is especially useful for:
- master scene planning
- `master_scenes.json` creation
- prompt generation

The application should:
- prepare files
- call the AI agent
- collect outputs
- validate outputs
- merge structured results
- update workflow column state in the UI

This makes Tool 1 much more automatable and easier to reason about.

## 18. Brief Explanation of Tool 2 for Context

Tool 2 is the multilingual final assembly tool.

For each language, Tool 2 will take:
- localized narration
- localized `timeline_LANG.json`
- shared assets
- optional localized SRT

and produce:
- the final localized video

That means Tool 1 must output clean shared artifacts and clean per-language timing artifacts.

Tool 2 depends on Tool 1’s outputs being explicit and stable.

## 19. How Tool 1 Outputs Will Be Used Later

### `master_scenes.json`
Used to lock shared scene identity across channels.

### `prompt_list.txt`
Used by a human to generate the shared visuals once.

### `asset_manifest.json`
Used by Tool 2 to map shared assets back to scenes.

### `timeline_LANG.json`
Used by Tool 2 to retime the shared visuals for each narration.

### `srt_LANG.srt`
Used for review and optional subtitle handling later.

## 20. Short Tool 1 Workflow

**master script > master scene planning > prompt list > human shared asset generation > for each language: translation > voice generation > subtitle alignment > localized `timeline_LANG.json`**

Tool 1 is now the multilingual planning and pre-generation engine of the project.

It merges:
- translation
- voice generation
- subtitle timing
- master scene planning
- localized timeline creation
- prompt generation

Its mission is:

**define scenes once, generate shared assets once, and generate localized timing layers for many narrations and channels.**
